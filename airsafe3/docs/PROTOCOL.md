# AIRSAFE data-integrity protocol (v1)

Goal: anyone can check that a stored sensor reading is **unchanged since it was recorded**, **which device produced it**,
and **when it existed at the latest**, without trusting the operator of the server.

Three independent implementations must agree byte for byte: the Rust server (`backend/src`), the JavaScript reference
(`tools/lib/web3ref.mjs`, also used by `tools/verify_proof.mjs` and `tools/sim_device.mjs`) and the browser verifier
(`web/lib/verify.js`). `backend/fixtures/web3_vectors.json` is generated by the reference and checked by
`cargo test` (`backend/tests/web3_vectors.rs`) and `web/test/verify.test.mjs`.

## 1. Identities

| Who | Key | Identifier |
|---|---|---|
| Device | Ed25519, private key only on the device | `did:key:z6Mk...` (multicodec 0xed01 + 32-byte public key, base58btc) |
| Server | Ed25519 (`SERVER_SIGNING_KEY`, else generated and kept in the database) | `did:key`, published at `GET /api/ledger/server-key` |
| Operator account | secp256k1 wallet (optional login) | Ethereum address (EIP-55) |
| Anchoring account | secp256k1 key paying for anchor transactions | Ethereum address |

## 2. Submitting a reading

`POST /api/ingest/reading`, headers `X-Device-Id`, `X-Device-Key` (API key, only its SHA-256 is stored) and, for devices
with a registered key, `X-Device-Signature`.

* Body: the JSON reading, **exact bytes** as sent (UTF-8).
* Signature: base64url (no padding) of the Ed25519 signature over  
  `"AIRSAFE-READING-V1\n" + device_id + "\n" + body_bytes`.
* If the device has a registered public key and a signature is present it MUST verify (else 401). If the device was
  provisioned with `require_signature`, a missing signature is 401. A verified reading is `attested = true`.
* `reading_ms`: the device's `ts` (unix seconds) times 1000 when within 7 days in the past and 5 minutes in the future of
  the server clock, otherwise the server receive time (ms).

## 3. Ledger leaf

```
leaf_input = "AIRSAFE-LEAF-V1|" + device_id + "|" + reading_ms + "|" + hex(sha256(body)) + "|" + (signature or "-")
leaf_hash  = SHA-256( 0x00 || leaf_input )                 // RFC 6962 leaf hash
```
Every reading from a provisioned device gets a leaf (signed or not). Simulated data never does.

## 4. Batches and checkpoints

Periodically (and on demand) the server takes up to 4096 unbatched leaves in ascending reading id and builds an
**RFC 6962 Merkle tree** (node hash `SHA-256(0x01 || left || right)`, split at the largest power of two below n).

```
checkpoint_message   = "AIRSAFE-CHECKPOINT-V1|" + batch_id + "|" + root_hex + "|" + leaf_count + "|" + from_ms + "|" + to_ms
checkpoint_signature = base64url( Ed25519_server( checkpoint_message ) )
```

## 5. Anchoring on an EVM chain

`contracts/src/AirSafeAnchor.sol`, function  
`anchor(bytes32 root, uint64 batchId, uint64 leafCount, uint64 fromMs, uint64 toMs)`  
(selector `keccak256("anchor(bytes32,uint64,uint64,uint64,uint64)")[0..4]`, five 32-byte words).
The server signs a plain EIP-155 legacy transaction with `ANCHOR_PRIVATE_KEY` and sends it with `eth_sendRawTransaction`.
The call is idempotent for an identical (batchId, root) so a crash between sending and recording is harmless.
The contract stores only roots, never sensor data.

## 6. Verifying a reading (what `verify_proof.mjs` and the web app do)

`GET /api/ledger/proof/{reading_id}` returns the raw reading, `leaf_input`, `audit_path`, `index`, `tree_size`, `root`,
the batch with `checkpoint_signature` and the anchor, and the server key. A verifier then checks, **without trusting any
of the server's own conclusions**:

1. `leaf_input` and `leaf_hash` recomputed from the raw reading;
2. the device signature against the device public key (`attested` readings);
3. the Merkle inclusion proof (RFC 9162 section 2.1.3.2) reaches `root`;
4. `checkpoint_signature` verifies under the server public key over the checkpoint message;
5. (with an RPC endpoint) the anchor transaction's calldata equals `anchor(root, batchId, ...)` for this root, its
   receipt succeeded, and `isAnchored(root)` is true on the contract.

## 7. What this proves, and what it does not

Proves: the reading was recorded unchanged no later than the anchor block time; a signed reading came from the holder of
the device key; the operator could not have edited it afterwards without the change being detectable.

Does **not** prove: that the sensor measured reality (a miscalibrated or physically tampered sensor produces correctly
signed wrong numbers); that readings were not omitted before submission (completeness needs device-side counters, not in
v1); anything about simulated data. Until a batch is sealed (minutes) and anchored, the guarantee is weaker: sealing
fixes the data against later edits by anyone who cannot also re-sign the checkpoint, anchoring removes that dependence.

## 8. Wallet sign-in (EIP-4361)

`POST /api/auth/wallet/nonce {address}` returns a server-built message (domain, address, statement, URI, chain id, nonce,
issued-at, 10-minute expiry). The wallet signs it with `personal_sign` (EIP-191). `POST /api/auth/wallet/verify
{address, nonce, signature, role?, vertical_access?}` consumes the nonce atomically, recovers the signer from the signature
over the **stored** message and compares it with the address. Unknown wallets are only created when a role is supplied
(registration). Same JWT as email login afterwards.
